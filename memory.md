# Memory

## Decisions
- 2026-09-11: Merged the "item list" and "comparison view" into one currency-grouped list (sorted cheapest-first per group) with inline Edit/Remove, instead of two separate lists — avoids re-reading the same numbers twice on a small screen while shopping.
- 2026-09-11: All prices and currency codes render in monospace (IBM Plex Mono), right-aligned, as the app's visual signature — supports fast numeric scanning in-store rather than generic form styling.
- 2026-09-11: One form component serves both Add and Edit (pre-filled, button label/heading swap) instead of a separate edit UI, to avoid maintaining duplicate markup.
- 2026-09-11: MVP (Phase 1) ships with manual entry only — no Shopee/Lazada scraping. Reason: those sites block most server-side fetches, so a working comparison tool must not depend on auto-fetch succeeding. Scraping is Phase 2 per todo.md.
- 2026-09-11: Redesigned to a dark "scanner/price-tag terminal" visual concept (Big Shoulders/IBM Plex Sans/IBM Plex Mono, scan-red + tag-gold accents, die-cut Best Value badge) after the user explicitly disliked the original light SaaS-card look. Drafted as a standalone preview and confirmed before touching production files.
- 2026-09-11: Removed per-item currency for one global "Comparing in" setting — the real use case turned out to be comparing multiple offers of the *same* product (same currency), not tracking arbitrary items across currencies. Supersedes the earlier "currency codes render per item" part of the visual-signature decision above — only price itself is still monospace/right-aligned per item now.
- 2026-09-11: Product name field now remembers the last-typed name across adds, since comparing offers of the same product means the name rarely changes between entries.
- 2026-09-11: "Clear all" reuses the existing single-item-remove's non-blocking 5-second undo-toast pattern rather than a confirm dialog, consistent with the no-confirm-dialogs decision below.
- 2026-09-13: Of the 5 promo types, only Fixed bundle price disables the new Pack count field — its own N/X params fully replace both Price and Pack count for that listing. BOGO, 2nd item 50% off, buy3pay2, and 2nd item at a fixed price all still use the Price field as the cost of one pack, so Pack count stays enabled and composes with each promo's own multiplier (e.g. a 6-pack BOGO correctly divides by 6×2=12 base units). Initially misstated during planning as "Fixed bundle and 2nd-item-fixed both disable it" — caught and corrected before implementation by re-checking which promo formulas actually use the Price field vs. ignore it entirely.
- 2026-09-13: For Phase 4c (photo-assisted entry), chose regex/heuristics over a second vision-capable LLM call to structure OCR text into `{name, price, unitSize, ...}`, even though the spec left this open as either option. Reason: the spec only named Azure AI Vision as the new dependency; a second LLM provider would be an unnamed paid service per this project's tech-stack rule. Revisit only if regex proves too fragile against messy in-store photos, and only with an explicitly named provider.
- 2026-09-13: Phase 4b persistence saves to `localStorage` immediately on every mutation, including remove — a removed item is gone from storage right away, and the 5-second Undo toast is purely an in-memory splice-back on top, not something storage waits on. Chosen over "wait for the undo window to expire before persisting" for simplicity — the undo toast's job is visual/in-session forgiveness, not a storage transaction boundary.
- 2026-09-14: Replaced the "Unit of measure" `<select>` with a pill/radiogroup selector (ml/l/g/kg/piece/sheet, shown as full words: Milliliters/Liters/Grams/Kilograms/Piece/Sheet) after the user called the dropdown bad UX. product-designer moved it out of its old side-by-side `.field-row` with Unit size into its own full-width row — full words like "Milliliters"/"Kilograms" don't fit the ~150px side-by-side column at any viewport width, and a full-width flex-wrap row avoids truncation without needing a fixed grid. Underlying stored values are unchanged (still the short codes), so no localStorage migration was needed. Selection also now persists across adds via a `lastUnitOfMeasure` variable, mirroring the existing `lastProductName` behavior.
- 2026-09-14: Added a non-blocking plausibility warning on Unit size for l/ml/kg/g (e.g. "Unusually large for Liters — did you mean Milliliters?"), after the user twice entered magnitude typos (2800 l of detergent, 1000 l of rice) that silently won Best Value. Thresholds (l>30, ml>5000, kg>50, g>10000) assume a single consumer package is never sold in tens of liters/kilograms. Deliberately non-blocking — doesn't prevent Add Item — consistent with this project's no-confirm-dialogs/no-hard-blocks decision; piece/sheet have no threshold since pack sizes for those are legitimately very variable.
- 2026-09-14: Replaced the flat "Best Value" list entirely with a per-product ranked-offers view (user loved a reference mockup and asked to build toward it) — items now group by product name first (each distinct name = its own numbered 01/02/03… block, ordered by first-added), with a relative-cost bar per row (width = thisOffer/mostExpensiveOffer), a computed insight sentence ("you'd pay ฿X more per litre/kilo/piece with the priciest option"), and a single-offer fallback (no bar/banner, just a quiet "add another to compare" note) when a product has only one entry. Offer labels ("Qty 2", "+ shipping", a promo description) are auto-derived from existing fields rather than a new free-text field — user chose this over adding a manual "seller name" input to keep the data model simple. Form was also redesigned to a compact Price/Shipping and Size/Pack two-column layout with a live "Preview" line showing the per-unit price as you type, reusing `computeItemPrice()` against a throwaway item built from current field values rather than duplicating the math.

## Rejected Approaches
- 2026-09-11: Confirm dialog on item removal — rejected in favor of a 5-second undo toast, since this is a single-session low-stakes tool and a blocking dialog slows down repeated add/remove while comparing items in a shop.
- 2026-09-11: Built full Shopee/Lazada auto-fetch (cURL backend, domain allowlist, JSON-LD/OG/regex parsers, "Fetch from clipboard" UI) and later removed it entirely at the user's request. Lazada auto-fetch worked correctly end-to-end; Shopee never did (confirmed empirically — it serves an empty SPA shell to non-browser requests). The user found the "try then fail" flow frustrating for Shopee, their primary platform, and chose full manual entry over a feature that only worked for one of two target platforms. Alternatives discussed but not built: a headless-browser backend (rejected — outside the plain PHP/JS/HTML/CSS stack) or a bookmarklet/userscript run in the user's own browser (not rejected, just not requested).

## Gotchas
- 2026-09-11: A flex-layout bug (`.item-card-price` had `flex-shrink:0`, `.item-original` had `white-space:nowrap`) only surfaced with long unit labels/product names at mobile width. The builder's own automated pass missed it because it tested with typical short values; independent QA caught it by deliberately trying a long unit label. Worth testing long/edge-length text specifically for any future layout work here.
- 2026-09-11: Project has a GitHub repo connected (github.com/eeenismz/Price-Compare) set up outside Claude Code, with a GitHub-default README already committed before this session's rewrite — not something Claude Code initialized. No .gitignore existed yet; one was added per the Rule 9 baseline before the first commit through this workflow.
- 2026-09-11: `.toast` and `.field-row` both set an explicit CSS `display`, which silently overrides the browser's default `[hidden] { display: none }` — author CSS always beats user-agent CSS at equal specificity, regardless of the `hidden` attribute. Caused the Undo toast to always show and the bundle-promo fields to always render, undetected through several QA passes since nothing throws or looks broken in a static screenshot. Fixed with one defensive `[hidden] { display: none !important; }` rule. Worth checking for this pattern before adding `display:` to any selector that's also toggled via `hidden`.
- 2026-09-12: In the promo/quantity math system, `units(promo)` only controls how the shipping fee gets divided — it has no effect on the base price. The effective price comes entirely from `compute(price, promo)`. When adding quantity-based division, only `units()` was updated at first; `compute()` was left untouched, so the price silently never got divided (shipping math looked right, but the actual comparison price didn't) until caught via live browser testing against the user's real example. Any future promo type must divide the price inside `compute()`, not just report the unit count in `units()`.
- 2026-09-11: The original Phase 2 design research used a non-existent Shopee shortlink domain (`shope.ee`) instead of Shopee's actual native share-link domain (`shp.ee`, e.g. `th.shp.ee`) — only caught when the user pasted a real link from their phone's share sheet. Domain/API assumptions in scraping-adjacent research should be verified against a real, user-provided example, not trusted from research alone.
- 2026-09-13: A `<select>` element's default value is whatever HTML `<option>` has the `selected` attribute (or the first option, absent that) — it does NOT follow whatever a JS `resetForm()`/init function later intends as the default. On Phase 4a's first implementation pass, `js/app.js` correctly set the Unit-of-measure select to "piece" inside `resetForm()`, but nothing calls `resetForm()` on initial page load (same as the app's pre-existing init pattern), so the dropdown visually showed "ml" (the first `<option>`) until the very first Add/reset. Caught via live browser testing, not code review. Any new `<select>` with an intended default needs the `selected` attribute in the HTML itself, not just a JS default.
- 2026-09-14: When the results view was rewritten to group by product name, a new `productNameOrder` array was added to track display order — but it's only ever appended to inside the add-item submit handler, never seeded from items restored via `localStorage` on page load. Net effect: a hard refresh with existing saved items rendered a completely empty results panel (no error thrown, no console output — `renderResults()` silently iterated an empty array) even though the items themselves loaded fine into memory. Caught immediately by loading the real app in a browser rather than trusting the implementing subagent's "all tests pass" report — that subagent has no browser tool access and cannot actually verify UI behavior, only static/syntax checks. Any array used to drive render order alongside `items` needs to be rebuilt from `loadState()`'s output, not just appended to on user actions. Also worth remembering generally: a fast-worker/implementation pass's own "live-tested" claims are not verifiable by that agent and must be independently checked in a real browser before trusting them.
- 2026-09-13: `fixedBundle`'s math (`totalCost = promo.x`, ignoring `item.price` entirely) was implemented correctly, but the results card's "original price" display line still unconditionally led with `item.price.toFixed(2)` for every promo type — so a bundle item showed its unused/irrelevant Price value as if it were the charged price, while the actual math correctly used the bundle's X. This is exactly the "Price field silently means something else" confusion this whole rewrite exists to fix, and it slipped through code review (the compute logic was correct) — only caught by adding a real fixedBundle item in the browser and reading the rendered card. Worth checking every promo-conditional display string against which fields the compute function for that type actually reads, not just checking the compute function itself.
